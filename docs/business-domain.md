# Business Domain

This document describes the core concepts, actors, rules, and workflows of the English Learning App as reflected in the current codebase.

## Product Purpose

Support **English speaking practice** through topic-based questions, spoken or typed answers, and **automated scoring/feedback** (designed via Gemini AI). The system also supports **level assessment** to classify learners as BEGINNER, INTERMEDIATE, or ADVANCED.

## Actors and Roles

| Role (`RoleName`) | Description | Default on register |
|-------------------|-------------|---------------------|
| `LEARNER` | Takes practice/assessment; views own history | Yes |
| `MENTOR` | Defined in schema; limited API use today | No |
| `ADMIN` | Manages topics, questions, users via frontend admin | Assigned in seed data |

User account states (`UserStatus`): `ACTIVE`, `DISABLE` (inactive users cannot log in).

## Core Domain Concepts

### Topic

A **theme** for speaking practice (e.g. travel, work). Attributes:

- `topicName`, `description`
- `difficultyLevel` (BEGINNER | INTERMEDIATE | ADVANCED)
- Optional `creator` (User)

Topics group **Questions**.

### Question

A **prompt** the learner responds to. Stored as `description` (the question text). Attributes:

- Linked to one `Topic`
- `difficultyLevel` for filtering (especially in assessments)
- `creator` (User)

In the UI, questions are sometimes referred to as "sentences" (legacy/mock naming).

### Practice Session

A **single learning attempt** by a user. Attributes:

- `sessionType`: `PRACTICE` or `ASSESSMENT`
- `startedTime`, `endedTime`
- `score` (aggregate, typically 0–100 scale per session design)
- Links to `User` and optionally `Topic`

Sessions contain an ordered set of **PracticeQuestion** rows (session ↔ question many-to-many via composite key).

### Practice Answer

The learner's **response** to one question in a session:

- `userAnswer` (text; often speech transcript)
- One optional **Feedback** per answer

### Feedback

**Evaluation result** for one answer:

- `overallScore` (0–100 per question in AI design)
- `feedbackText` (examiner comments; full Gemini response may be stored)

Generated by **GeminiAIService** in code, but persistence flow is not wired end-to-end.

### Assessment

A **formal level test** tied 1:1 to a `PracticeSession` of type `ASSESSMENT`:

- `score` — sum of per-question feedback scores at commit time
- `levelAssigned` — derived band: BEGINNER / INTERMEDIATE / ADVANCED
- `takenDate`

One user may have many assessments over time.

### Profile

Extended learner information (1:1 with User):

- Name, birth date, occupation, `target_goal`
- `level` on profile (separate from assessment-assigned level)

### Subscription and Plan (planned)

Entities exist (`Plan`, `Subscription`, `PlanName`, `SubscriptionStatus`) for monetization but **no active business services or APIs** in the current application layer.

### Admin Log (planned)

`AdminLog` records admin actions (`ENABLE_USER`, `DISABLE_USER`, etc.) — schema only; no write path in services.

## Business Rules

### Registration

1. Email normalized (lowercase, trim) and must be unique.
2. Password stored as BCrypt hash.
3. New users receive `LEARNER` role automatically.
4. Status set to `ACTIVE`.

### Login

1. Only `ACTIVE` users may authenticate.
2. JWT embeds email and **first** role from `userRoles`.
3. Invalid credentials return unified error (no email enumeration distinction in exception type).

### Assessment — Start

Implemented in `AssessmentServiceImpl.startAssessment`:

1. Create `PracticeSession` with `sessionType = ASSESSMENT`.
2. Select a **random topic** from the database.
3. Generate **10 questions** from that topic:
   - 4 × BEGINNER
   - 3 × INTERMEDIATE
   - 3 × ADVANCED
4. Fail if insufficient questions exist for any band.
5. Link questions via `PracticeQuestion` rows.
6. Return `sessionId`.

> **Implementation note:** `practiceSession.setTopic(topic)` is not called in current code; history views that need `topicName` may fail for assessment-only sessions.

### Assessment — Commit

Implemented in `AssessmentServiceImpl.commitAssessment`:

1. Session must exist, belong to current user, and not already ended.
2. Load all `PracticeAnswer` for session (with feedback).
3. `totalScore` = sum of `feedback.overallScore` (answers without feedback contribute 0).
4. Set session `score`, `endedTime`.
5. Create `Assessment` with `levelAssigned`:
   - Total ≥ 80 → `ADVANCED`
   - Total ≥ 50 → `INTERMEDIATE`
   - Else → `BEGINNER`
6. Return `AssessmentResponse`.

**Gap:** Request body `answers` list is not used to create answers or invoke AI before commit.

### AI Evaluation (Gemini)

`GeminiAIServiceImpl.evaluateAnswer(question, answer)`:

1. Sends IELTS-style examiner prompt to `gemini-flash-latest`.
2. Expects response format: `SCORE: <0-100>` and `FEEDBACK: <text>`.
3. Parses score with regex; clamps to [0, 100].
4. Returns in-memory `Feedback` (not saved).

**Intended use:** Call when learner submits each answer; persist `PracticeAnswer` + `Feedback` before commit.

### Practice (informal)

Designed for topic-based rehearsal (`SessionType.PRACTICE`):

- `POST /api/user/practice/start` is **commented out** in controller.
- History and detail endpoints **read** existing sessions only.

### Content management (admin)

Admins (frontend) manage:

- Topics — CRUD on `/api/topics`
- Questions — CRUD on `/api/questions`
- Users — list, lookup by email, toggle status

Backend does not enforce `ROLE_ADMIN` on topic/question endpoints; any authenticated user can call them. Only `/api/admin/**` is strictly admin-gated (and unused).

## User Journeys

### Journey A — Register and login (working)

1. Register with email/password.
2. Login → receive JWT.
3. Frontend stores token; subsequent API calls authenticated.

### Journey B — Admin manages content (working)

1. Admin logs in (seed user with ADMIN role).
2. Redirected to `/admin`.
3. Create/edit topics and questions.
4. Manage user active/disabled status.

### Journey C — View practice history (partial)

1. Learner opens `/history`.
2. Frontend calls `GET /api/user/practice/history`.
3. Displays sessions **if** they exist in DB (requires prior session creation flow).

### Journey D — Speaking practice (broken / mock)

1. Learner opens `/speaking`.
2. Loads topics; selects topic and question.
3. Records speech via browser API.
4. **Mock score** displayed; save API not connected.

### Journey E — Level assessment (backend only)

1. `POST /api/user/assessment/start` → `sessionId`.
2. *[Missing]* Submit each answer + AI feedback.
3. `POST /api/user/assessment/commit` → level and score.
4. `GET /api/user/assessment/history` and `GET /api/user/assessment/{id}` for review.

Frontend does not implement Journey E.

## Glossary

| Term | Meaning in this project |
|------|-------------------------|
| Session | `PracticeSession` — container for one practice or assessment run |
| Sentence | UI/mock term; backend entity is `Question` |
| Score (session) | Aggregate stored on session/assessment |
| Score (feedback) | Per-question 0–100 from AI |
| Level | `Level` enum: BEGINNER, INTERMEDIATE, ADVANCED |
| Commit | Finalize assessment and persist results |
